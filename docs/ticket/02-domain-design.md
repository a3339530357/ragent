# 比特严选 · 售后客服与工单系统 —— 领域设计

> 状态：设计草稿（2026-11-04），尚未动代码。
> 基座：现有 Ragent（Java 17 / Spring Boot / AgentScope）+ 比特严选演示数据集（`resources/initializer/bit-selection`）。

## 0. 一句话

客户在对话页找客服 Agent，答得了就直接答；答不了由**工单 Agent** 建单，**后端规则**定优先级、算 SLA、派给坐席，**处理 Agent** 帮坐席查数据、办业务，高风险动作要**坐席审批**，每次对客回复和结单都过**质检 Agent**。坐席在新做的**工单工作台**里看全部过程。

设计底线：**模型只负责"理解和建议"，状态、权限、时限、钱，全部由后端代码决定。**

## 2. 角色与边界

| 角色 | 是谁 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 客户 | 平台普通用户（`user`） | 在对话页咨询、确认写操作、补充信息 | 看不到工单内部流转和其他客户的数据 |
| 坐席 | 新增角色 `staff`（演示时可由 `admin` 兼任） | 认领/处理/转派工单、审批高风险动作、结单 | 不能越过状态机直接改状态 |
| 组长 | `staff` + `lead` 标记 | 接收 SLA 升级、强制转派 | — |
| 客服 Agent | AI | 意图识别、知识库问答、**只读**查订单/物流 | 不能建单以外的写操作，不能退款 |
| 工单 Agent | AI | 把对话整理成结构化工单要素 | 不决定优先级、不选处理人 |
| 处理 Agent | AI | 为坐席查数据、生成处理方案、发起业务操作 | 高风险操作只能"提申请"，不能直接执行 |
| 质检 Agent | AI | 给回复和处理结果打分、标问题 | 不改任何业务数据 |

## 3. 数据模型（业务库 `ragent_bit`）

### 3.1 `t_ticket` 扩展

在现有 8 个字段基础上增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ticket_no` | 改为由序列 `seq_ticket_no` 生成 | 修掉 count+1 的并发撞号 |
| `priority` | `VARCHAR(4)` | `P0`–`P3`，后端规则算出（§5） |
| `order_no` | `VARCHAR(32)` 可空 | 关联订单 |
| `after_sale_id` | `BIGINT` 可空 | 关联售后单 |
| `conversation_id` | `VARCHAR(64)` | 关联客户对话，工作台据此回放 |
| `skill_group` | `VARCHAR(32)` | 由分类映射：订单组 / 售后组 / 投诉组 |
| `assignee_id` | `VARCHAR(20)` 可空 | 当前处理人 |
| `first_response_due` | `TIMESTAMPTZ` | 首响截止时间 |
| `resolve_due` | `TIMESTAMPTZ` | 解决截止时间 |
| `first_responded_at` / `resolved_at` / `closed_at` | `TIMESTAMPTZ` | 实际时间点，用于算 SLA 达成率 |
| `escalation_level` | `SMALLINT` 默认 0 | 升级次数 |
| `ai_suggestion` | `JSONB` | 工单 Agent 的原始建议（分类、信号、置信度），**只存档不生效** |
| `idempotency_key` | `VARCHAR(64)` 唯一 | 防同一对话重复建单 |
| `version` | `INT` 默认 0 | 乐观锁 |

状态字段沿用中文值（现有 `submit_ticket` 写的就是"待受理"），代码里用枚举映射，不破坏兼容。

### 3.2 新表

```text
t_ticket_event      工单事件流水（审计 + 工作台时间线）
  id, ticket_id, action, from_status, to_status,
  actor_type(system|ai|staff|customer), actor_id,
  payload JSONB, trace_id, created_at

t_staff             坐席

t_approval          坐席审批单（人工介入）

t_tool_call_log     写操作幂等与重试记录

t_qa_result         质检结果

```

## 4. 工单状态机

### 4.1 状态

| 状态 | 含义 |
|---|---|
| 待受理 | 已建单，等待分派（沿用现有值） |
| 已分派 | 已有处理人，还没开始处理 |
| 处理中 | 坐席（借助处理 Agent）正在处理 |
| 待审批 | 有高风险动作在等审批 |
| 待客户补充 | 缺信息，等客户回复（**暂停 SLA 计时**） |
| 已解决 | 方案已执行、已回复客户 |
| 已关闭 | 客户确认，或解决后 72 小时无异议自动关闭 |
| 已撤销 | 客户主动撤销，或判定为重复工单 |

### 4.2 流转规则

```text
            ┌────────── 撤销 ───────────────────────────────┐
            │                                               ▼
 [待受理] ──分派──▶ [已分派] ──开始处理──▶ [处理中] ──提交方案──▶ [已解决] ──确认/超时──▶ [已关闭]
                        ▲                   │  ▲  │                 │
                        │转派               │  │  └─缺信息─▶[待客户补充]   │客户不满意
                        └───────────────────┘  │       │客户回复       ▼
                                   发起审批 ▼  └───────┘            [处理中]
                                        [待审批] ──批准(执行成功)/驳回──▶ [处理中]
```

| 动作 | 从 | 到 | 谁能触发 | 守卫条件 |
|---|---|---|---|---|
| 分派 | 待受理 | 已分派 | 系统 | 找到有余量的坐席 |
| 开始处理 | 已分派 | 处理中 | 坐席（本人） | `assignee_id = 当前用户` |
| 转派 | 已分派/处理中 | 已分派 | 坐席、组长 | 目标坐席在线且有余量 |
| 发起审批 | 处理中 | 待审批 | 处理 Agent / 坐席 | 动作属于高风险清单（§7） |
| 审批完成 | 待审批 | 处理中 | 坐席 | 不能审批自己发起的单子 |
| 缺信息 | 处理中 | 待客户补充 | 坐席 | — |
| 客户回复 | 待客户补充 | 处理中 | 系统 | — |
| 提交方案 | 处理中 | 已解决 | 坐席 | 没有未决的审批单 |
| 重开 | 已解决 | 处理中 | 客户 | 解决后 72 小时内 |
| 关闭 | 已解决 | 已关闭 | 客户 / 系统 | 客户确认，或超过 72 小时 |
| 撤销 | 待受理/已分派/处理中 | 已撤销 | 客户、坐席 | 没有已执行的资金动作 |

### 4.3 实现要点

- 所有流转只走一个入口：`TicketStateMachine.transition(ticketId, action, actor, payload)`。
- 规则用一张"动作 → 允许的来源状态 / 角色 / 守卫"的表驱动，非法流转直接拒绝，**不交给模型判断**。
- 写库用条件更新：`UPDATE t_ticket SET status=?, version=version+1 … WHERE id=? AND status=? AND version=?`。影响 0 行就说明被别人抢先改了，返回冲突；同一事务里写 `t_ticket_event`。
- AI 只能通过工具**请求**流转（例如"发起审批"），工具内部也调同一个入口，享受同样的校验。

## 5. 优先级（规则算，模型只提供信号）

工单 Agent 输出结构化信号，后端按规则打分：

| 信号 | 来源 | 规则 |
|---|---|---|
| 安全隐患（电池鼓包、冒烟、发烫） | 模型抽取 + 关键词兜底 | 直接 **P0** |
| 订单实付金额 | 查库 | ≥ 5000 元 +2；≥ 1000 元 +1 |
| 客户明确投诉或情绪激烈 | 模型抽取 | +1 |
| 同一订单 24 小时内重复进线 | 查工单表 | +1 |
| 已超过平台承诺时效（如超时未发货） | 查订单/物流 | +1 |

总分 ≥ 3 为 P1，等于 2 为 P2，其余为 P3。模型给的信号和规则结果都写进 `ai_suggestion`，方便事后核对"模型说了什么、系统最后怎么定的"。

## 6. SLA 与分派

### 6.1 时限

| 优先级 | 首响 | 解决 |
|---|---|---|
| P0 | 15 分钟 | 4 小时 |
| P1 | 1 小时 | 24 小时 |
| P2 | 4 小时 | 48 小时 |
| P3 | 24 小时 | 72 小时 |

演示时通过配置把所有时限缩短（例如除以 60），现场就能看到超时升级。按工作日历计时（扣掉夜间和节假日）列为二期。

### 6.2 超时怎么触发 —— 选定时扫描，不选延时消息

- 做法：每分钟扫一次 `resolve_due / first_response_due < now()` 且未结束的工单，用条件 UPDATE 升级，保证多实例同时扫也只升级一次。与现有的 `BitPendingOrderTimeoutTask` 是同一套路。
- 不用 RocketMQ 延时消息的理由：截止时间会变（调优先级、"待客户补充"暂停计时），延时消息发出去就撤不回，到点了还得再查库确认；而且现有生产者也没有封装延时发送。扫描以数据库为准，天然幂等，演示环境足够用。量大以后再换成"时间轮 / 延时消息 + 查库确认"。
- 75% 时限时预警（工作台标黄）；到期时 `escalation_level + 1`、通知组长、优先级上调一级。

### 6.3 分派

1. 分类 → 技能组（订单问题→订单组，商品/售后问题→售后组，投诉建议→投诉组）。
2. 组内选**在线、未满载**（处理中工单数 < `max_load`）的坐席，取负载最小的；负载相同时，取最久没被分派过的。
3. 用条件更新给坐席占名额，防止并发时超载；没人可派就留在"待受理"，由扫描任务重试并在工作台标红。

模型不参与选人。

## 7. 多 Agent 编排

### 7.1 拓扑（编排写在代码里，不是让一个"主管模型"临场决定）

```text
客户消息
   │
   ▼
[客服 Agent] ──能直接答──▶ 回复客户 ──▶ (异步) [质检 Agent]
   │
   │ 需要人工 / 工具办不了 / 客户要求转人工
   ▼  handoff（结构化交接包）
[工单 Agent] ──▶ create_ticket（后端：算优先级 → 算 SLA → 分派）
                                │
                                ▼
                 坐席在工作台点"开始处理"
                                │
                                ▼
                         [处理 Agent] ◀──▶ 坐席
                           │      │
                 只读工具直接查   高风险动作 → 审批单 → 坐席批准 → 后端执行
                           │
                           ▼
                     提交方案 / 回复客户 ──▶ [质检 Agent]
```

### 7.2 交接（Handoff）

- 客服 Agent 只拿到一个交接工具 `handoff_to_ticket`，参数是结构化交接包：`{订单号, 问题摘要, 客户诉求, 已尝试的处理, 关键原话}`。
- 编排器收到交接后，用**交接包 + 必要的对话摘要**启动工单 Agent，而不是把整段聊天塞过去。这样上下文更短、更省 Token，也避免把客户的隐私字段带到不需要的环节。
- 每个 Agent 只挂自己那一组工具（最小权限）：

| Agent | 工具 |
|---|---|
| 客服 | 知识库检索、查商品/订单/物流/售后（只读）、`handoff_to_ticket` |
| 工单 | `create_ticket`、查订单（只读）、查重复工单 |
| 处理 | 全部只读查询、`apply_after_sale`、`request_approval`、`reply_customer`、`ask_customer` |
| 质检 | 无业务工具，只接收"回复 + 依据 + 工具结果" |

### 7.3 状态持久化与断点续跑

- 每个节点开始和结束时写 `t_agent_run.current_node / state`。
- 进程重启或等待人工（审批、客户补充信息）后，按 `current_node` 从断点继续，不重跑已完成的节点。
- 客户侧的多轮对话继续用 Ragent 现有的会话存储、记忆和上下文压缩。

### 7.4 和 LangGraph 的概念对照（面试用）

| LangGraph | 本项目 |
|---|---|
| StateGraph（节点 + 边） | 代码里的编排器 + 固定拓扑 |
| State | `t_agent_run.state` + 工单本身 |
| Checkpointer | `t_agent_run` 按节点落库 |
| `interrupt()` 人工介入 | 审批单 `t_approval`，状态变为"待审批"后挂起 |
| Handoff / Command(goto) | `handoff_to_ticket` 工具 + 编排器路由 |

## 8. 人工介入（两种，别混）

| | 客户确认（已有） | 坐席审批（新增） |
|---|---|---|
| 谁点 | 客户 | 坐席 |
| 触发 | 写操作工具（`readOnly=false`），例如下单、改地址 | 高风险动作清单 |
| 实现 | AgentScope 确认流程 | `t_approval` + 工单变为"待审批" |

高风险动作清单：退款金额 ≥ 500 元、换货、发补偿券、超出政策的特殊处理。

关键规则：**批准后执行的是审批单里冻结的参数快照**，不再让模型重新生成一遍。否则模型可能在批准之后又改了金额。

## 9. 工具调用：重试与幂等

1. **幂等键**：写操作的幂等键 = `工单号或对话 ID + 动作 + 业务参数` 的哈希；审批执行时直接用审批单的幂等键。
2. **执行前**先占位 `t_tool_call_log`（主键冲突就说明已经执行过或正在执行，直接返回上次的结果）。
3. **错误分三类处理**：

| 类型 | 例子 | 处理 |
|---|---|---|
| 临时错误 | 超时、连接失败、5xx | 退避重试，最多 2 次 |
| 业务拒绝 | 已超过退货期、库存不足 | 不重试，原因交给模型组织回复 |
| 结果未知 | 请求发出去了但超时 | **先按幂等键查结果**，确认没执行成功再重试 |

4. 模型自己重复调用（同一轮发两次相同的工具调用）也会被幂等键挡住。

## 10. 质检 Agent 与 LLM-as-Judge（让模型当评委打分）

### 10.1 在线质检

- 对客回复和结单后，通过 MQ 异步触发，不拖慢回复。
- 输入：回复原文、引用的知识片段、本轮工具返回的数据、适用的政策条款。
- 打分维度（每项 1–5 分，必须附证据）：

| 维度 | 检查什么 |
|---|---|
| 准确性 | 回复里的订单状态、金额、时效是否和工具返回一致 |
| 有依据 | 政策类说法能不能在知识库里找到出处 |
| 合规 | 有没有超出政策的承诺、有没有泄露其他人的信息 |
| 完整性 | 客户的诉求是否都回应了 |
| 语气 | 是否得体（权重最低） |

- 总分低于阈值或"合规"不及格 → 工作台标红，进入人工复核列表。

### 10.2 离线评测集

- 约 50 条用例：取自比特严选的 15 条示例问题，再加构造的售后场景（退货、换货、超时未发货、电池安全、重复进线、恶意索赔）。
- 能用代码判的部分用代码判：分类、优先级、技能组、是否该转人工、是否触发审批。
- 不能用代码判的部分交给评委模型打分。
- **先校准评委**：抽 20 条人工打分，和评委模型对比一致率，一致率不够就改评分标准，不要直接拿评委分数当结论。
- 每次改提示词或换模型都整套重跑，结果留档。现有的 `resources/regression/` 目录就是这个用法。

## 11. Trace 与 Token 成本

- 每次模型调用记录：所属 Agent、工单号、对话 ID、输入/输出/缓存命中 Token、耗时。
- 汇总口径：每张工单的 Token 和费用、各 Agent 的占比、各模型的单价表（配置化）。
- 工作台工单详情页显示"本单 AI 成本"；Agent 看板增加"按 Agent 角色"的维度。
- 基于现有 Trace 和请求 dump 扩展，不另起炉灶。

## 12. 工单工作台（前端）

路由放在管理后台下：`/admin/tickets`。

```text
┌ 工单列表 ───────────────────────────────────────────────────────────┐
│ [状态▼] [优先级▼] [只看我的] [即将超时]                              │
│ P0 TK…0003  电池鼓包      售后组  张三  处理中   ⏱ 剩 08:12 (红)    │
│ P1 TK…0002  超时未发货    订单组  李四  待审批   ⏱ 剩 41:30 (黄)    │
```

## 13. 分期与验收

| 期 | 内容 | 验收标准 |
|---|---|---|
| 0 | 灌入比特严选演示数据 | 对话页问"我的订单"能查到数据 |
| 1 | 工单表扩展 + 状态机 + 事件流水 + 序列号 | 状态机单测覆盖全部合法/非法流转；并发建单不撞号 |
| 2 | 优先级规则 + SLA 扫描 + 分派 | 缩短时限后能看到预警、升级；并发分派不超载 |
| 3 | 四个 Agent + 交接 + `t_agent_run` | 三个演示场景端到端跑通；中途重启能续跑 |
| 4 | 坐席审批 + 幂等/重试 | 重复批准、重复调用只执行一次 |
| 5 | 工作台前端 | 列表、详情、审批、SLA 倒计时可用 |
| 6 | 质检 + 评测集 + 评委校准 | 产出一份评测报告（这些就是面试里讲的数字） |
| 7 | Token 成本统计 | 工单详情和看板能看到成本 |

### 演示场景

1. **直接解决**：AirPods 有杂音 → 客服 Agent 查保修政策 + 订单 → 引导申请售后，不建单。
2. **建单流转**：下单三天没发货 → 交接 → 建单 P1、派订单组 → 处理 Agent 查物流 → 坐席回复。
3. **人工审批**：要求退款 2999 元 → 处理 Agent 提出退款申请 → 待审批 → 坐席批准 → 幂等执行；再点一次批准不会重复退款。
4. **SLA 升级**：缩短时限，放着不处理 → 标黄 → 升级给组长。

## 14. 已定的取舍（可推翻）

| 问题 | 先这么定 | 理由 |
|---|---|---|
| 编排框架 | Java 代码编排，不引入 LangGraph | 与现有技术栈一致；面试时讲概念对照 |
| 超时触发 | 定时扫描 | 截止时间会变，扫描天然幂等 |
| 坐席角色 | 新增 `staff`，演示期 `admin` 兼任 | 少改权限体系 |
| 工单表位置 | 业务库 `ragent_bit` | 工单属于商家业务，和订单在一起，方便同一事务处理 |
| 状态值 | 沿用中文 | 兼容现有 `submit_ticket` 和演示数据 |
