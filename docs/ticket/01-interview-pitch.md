- 背景照实说：基于开源的 Ragent 平台，以"比特严选"（一个虚构的 Apple 授权经销商）的售后业务为原型，**自己设计并实现**了客服与工单这一整块。

## 30 秒版

> 我做的是一个电商售后场景的多 Agent 客服与工单系统。客户咨询先由客服 Agent 结合知识库和订单数据直接回答；答不了的，由工单 Agent 整理成结构化工单，后端按规则定优先级、算 SLA、派给坐席；处理 Agent 帮坐席查数据、发起退款这类操作，高风险动作必须坐席审批；所有对客回复都过质检 Agent 打分。核心设计原则是：模型负责理解和建议，状态、权限、时限和钱都由后端代码决定。

## 2 分钟版

**背景**

> 电商售后客服有几个典型痛点。第一，大量咨询是重复的：订单到哪了、能不能退、保修多久，答案其实就在订单系统和政策文档里，但人工要在好几个系统之间来回切换。第二，需要人工的问题转工单全靠手填，分类经常错，优先级凭感觉，超时了也没人盯。第三，回复质量参差不齐，乱承诺、说错政策的情况很难被发现。
>
> 我以一个 Apple 经销商的售后业务为原型，在 Ragent 平台上做了这套客服与工单系统，拆成四个 Agent：客服、工单、处理、质检。

**解决的业务问题**

> **一是重复咨询自动解决。** 客服 Agent 做意图识别，政策类问题走知识库检索，订单、物流类问题调只读工具查实时数据。评测集上自动解决率 ___。
>
> **二是建单和分派标准化。** 客服 Agent 判断需要人工时，不是把整段聊天丢过去，而是交给工单 Agent 一个结构化交接包，包括订单号、诉求、已经试过什么。工单 Agent 只负责抽取分类和风险信号；优先级、SLA 截止时间、派给谁，都是后端规则算的，比如电池鼓包直接定 P0，同一订单一天内第二次进线要加分。分类准确率 ___。
>
> **三是 SLA 不漏单。** 工单状态机由后端管，所有流转只有一个入口，用条件更新加版本号防并发。超时用定时扫描触发，到 75% 预警，到期自动升级给组长。
>
> **四是高风险操作可控。** 退款超过阈值、换货、发补偿券这些动作，处理 Agent 只能提审批申请。坐席批准后，执行的是审批单里冻结的参数，不让模型再生成一遍。所有写操作带幂等键，重复批准、模型重复调用都只执行一次。
>
> **五是质量可度量。** 质检 Agent 按准确性、有依据、合规、完整性打分，低分进人工复核。离线有一套 ___ 条的评测集，评委模型先和人工标注做过校准，一致率 ___，每次改提示词都整套重跑。另外每张工单的 Token 成本可以追溯，平均每单 ___。

## 高频追问与答题要点

| 追问 | 要点 | 设计文档 |
|---|---|---|
| 为什么要拆成多个 Agent，一个不行吗？ | 工具越多选错越多；按职责拆开后每个 Agent 只挂自己的工具（最小权限），提示词更短，也能单独评测。代价是交接损失信息，所以交接用结构化包 | §7.2 |
| 哪些事不让模型做？为什么？ | 状态流转、优先级、SLA、分派、资金动作。这些要可审计、可复现，模型输出有随机性。模型给信号，规则下结论，两者都留档 | §0、§4、§5 |
| 状态机怎么防并发？ | 单一入口 + 表驱动规则 + `WHERE status=? AND version=?` 条件更新，影响 0 行就是冲突；同一事务写事件流水 | §4.3 |
| SLA 超时为什么不用延时消息？ | 截止时间会变（调优先级、等客户补充时暂停计时），延时消息撤不回；扫描以数据库为准、天然幂等。量大了换成时间轮加查库确认 | §6.2 |
| 幂等怎么做？结果未知怎么办？ | 幂等键先占位；错误分临时/业务拒绝/结果未知三类；结果未知时先按键查结果再决定要不要重试 | §9 |
| 人工审批之后模型会不会改参数？ | 不会，执行的是审批单冻结的参数快照 | §8 |
| LLM-as-Judge 靠得住吗？ | 先用人工标注校准一致率；能用代码判的（分类、优先级、是否该审批）不交给模型判；评委打分必须附证据 | §10.2 |
| 和 LangGraph 什么关系？ | 用 Java 在代码里编排；概念一一对应：StateGraph、Checkpointer、interrupt、Handoff | §7.4 |
| 发现过什么实际问题？ | 原有工单号用"当天数量 + 1"生成，并发会撞号，改成数据库序列 | §1 |
| 断了怎么续？ | `t_agent_run` 按节点落库，重启或等人工后从断点继续，不重跑已完成的节点 | §7.3 |
| Token 成本怎么控？ | 交接包代替整段历史、按角色选模型（质检可以用便宜模型）、按工单统计成本 | §7.2、§11 |
